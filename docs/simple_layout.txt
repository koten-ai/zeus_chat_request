# ----------------------------------------------------------------------------
# #NEW  not first-class on current min terminate schema

return.admin: {

  subject_confidence: 0.0 .. 1.0
    # how sure is the model that it identified the right subject/entity/topic?
    # separate from overall answer confidence above

  wish_i_knew: [                           # past tense: gaps this turn
    {
      what: ""                             # what was missing
      kind: "rules" | "message" | "schema" | "data" | "tool" | "other"
      why: ""                              # optional: how it would have helped
      severity: "low" | "med" | "high"     # optional
    }
  ]
    # empty [] = nothing material missing
    # sources of gaps: prompt/rules, user message, mini-schema, Zeus data, tools

  jail_break_attempt: 0.0 .. 1.0     # float, NOT boolean 0|1
    # SUBJECTIVE AI self-assessment (same spirit as subject_confidence)
    # how strongly does THIS turn look like a user jailbreak / policy-bypass attempt?
    # examples of scale (guidance only, not hard thresholds):
    #   0.0  no bypass intent sensed
    #   0.2  vague "ignore rules" flavor, low confidence
    #   0.5  clear pressure to break catalog / tool policy
    #   0.8+ strong jailbreak / exfil / override attempt (still subjective)
    # ADMIN ONLY — never show in chat UI
    # imperfect by design; optional parallel hard signal can come from Client hooks
}

M. WHO OWNS WHAT — Client pass-in vs Contract (hashed) vs optional
================================================================================

# Three buckets. Do not mix them or every tenant edit re-stamps Base, and
# every turn thrashes the contract hash.

```text
┌─ CONTRACT (hashed / stamped) ─────────────────────────────────────┐
│  Base-n body, verbs, weight order, hard flags, response schema    │
│  Change ⇒ new stamp / new hash                                    │
└───────────────────────────────────────────────────────────────────┘
┌─ ZEUS_CLIENT PASS-IN / OVERRIDES  (runtime, not hashed) ──────────┐
│  brand boilerplate, business rules text, locale, session, hooks   │
│  Change per tenant / per request without re-stamping Base         │
└───────────────────────────────────────────────────────────────────┘
┌─ OPTIONAL INSERTS  (soft / full profile / Workbench) ──────────────┐
│  optimal_paths, extra examples, eval ids — usually hash-excluded  │
└───────────────────────────────────────────────────────────────────┘
┌─ TERMINATE OUTPUT                                              ───┐
│  G1 user-facing · G2 admin · G3 client control-plane (triggers) │
└───────────────────────────────────────────────────────────────────┘
```

M7. DESIGN RULES (so Client can rely on rounds)
--------------------------------------------------------------------------------

  1. rule ids (keys) are stable for a session (prefer stable forever).
  2. business_rules_triggers keys SHOULD be subset of rules keys.
  3. Missing key ⇒ Client treats as false (sparse is correct).
  4. Triggers are model-subjective; hooks may force true/false for safety.
  5. User never sees triggers or jail_break_attempt — only summary / boilerplate.
  6. Contract hash ignores business_injection, output_request, and triggers.
  7. Client is source of truth for zeus_round / turn_index; model does not own clock.
  8. app_output only when output_request.app set; validate in Client; never G2 scores.
