    Simple picture: how it fits together
    
            
    You ask a question
        │
        ▼
  Zeus Client builds ONE model round:

  ┌─ PROMPT (one request — not three sends) ─────────────┐
  │  RULES (RED, hashed)  +  INJECT (BLUE)  +  MESSAGES  │
  └───────────────────────────┬──────────────────────────┘
                              ▼
                      LLM  ↔  Zeus tools
                              │ returns
                              ▼
  ┌─ OUTPUT ─────────────────────────────────────────────┐
  │  Layer A terminate (flat JSON)                       │
  │  G1 user · G2 admin · G3 client                      │
  └──────────────────────────────────────────────────────┘
        │
        ▼
  Zeus stores turn report (Layer B — not model-emitted)
    
            
    This repo holds baseline templates (by mode). Production catalogs are refined in Hub Workbench and stamped on your Zeus so the hash matches what you deploy. Full wire-order doc: docs/PROMPT_ASSEMBLY.md · diagram: images/assembled_prompt.svg.
    
          
    

          
    
            
    Assembled prompt (PROMPT vs OUTPUT)
    
            
    One model round has two big shells — not five separate “sends.” The Structure Assembly tab and README SVG match this.
    
            
      
              
    1. PROMPT (one request) =
                RULES +
                INJECT +
                MESSAGES[].
                Rules = hashed catalog system prompt + tools.
                Inject = not hashed (MINI-SCHEMA, company_context, rules[], hints…).
                Messages = the chat transcript. They are combined, not three sequential API calls.
      2. 
              
    2. LLM ↔ Zeus — model may call tools; results land back in messages for later rounds.
      3. 
              
    3. OUTPUT =
                Layer A terminate — one flat JSON object on return / terminating pipeline
                (G1 user · G2 admin · G3 client). Detective / spans = server Layer B after the model.
      4. 
            
    
            
    See Structure → Assembly tab, or Size map → Wire payload (catalog system+tools + optional blue estimates).
    
          
    

          
    
            
    Color policy (same on Cards · Size map · JSON)
    
            
      
              
    • RED — Rules. In the catalog; changing them changes the contract hash.
      • 
              
    • GREEN — Editable guidance. Often hash-excluded; often missing on min (yellow).
      • 
              
    • BLUE — Injected at runtime (not in this JSON). Competes for tokens with the system prompt.
      • 
              
    • PURPLE — Meta / stamp labels (id, hash, notes).
      • 
              
    • YELLOW — Expected on full profiles, absent on this min file (not always an error).
      •

    FAQ
    

          
    
            
    What is the difference between AUTO, ANALYTICS, FRAUD, …?
    
            
    Each file is a mode profile: same envelope idea (tools + rules), different emphasis.
    
            
      
              
    • analytics — default balanced demos
      • 
              
    • auto — discovery / setup; not long-term production
      • 
              
    • fraud — keep weak signals; graph-heavy
      • 
              
    • code / research / open — more exploratory mixes
      • 
              
    • tenant / private / regulated — stronger boundary posture
      • 
              
    • custom — operator shell
      • 
            
    
            
    This dropdown only switches which baseline you inspect. Production: assign a mode per scope in Zeus.
    
          
    

          
    
            
    Where do I put “talk about my business” for the AI?
    
            
      
              
    1. Hub Workbench / ScopeConfig — injects & entity map (preferred, BLUE).
      2. 
              
    2. guidance on a full catalog (GREEN, often hash-excluded).
      3. 
              
    3. Not by forever hand-editing public RED baselines if you care about stamp stability.
      4. 
            
    
          
    

          
    
            
    How do I optimize chat_request?
    
            
      
              
    1. Use Size map — shrink what dominates tokens.
      2. 
              
    2. Prefer min; keep evidence-loop terminate fields.
      3. 
              
    3. Push domain knowledge into MINI-SCHEMA + blue injects.
      4. 
              
    4. Prefer pipeline / cheaper verbs; drop unused tools.
      5. 
              
    5. Stamp on Zeus; A/B before promoting hashes.
      6. 
            
    
          
    

          
    
            
    What is the output scheme (Layer A vs B)?
    
            
    Layer A — model terminate on return / terminating pipeline.
    
            
      
              
    • Required (base-1 and base-4): summary, query_decomposition, decomposition, confidence (high|med|low).
      • 
              
    • Recommended (base-4+): policy_action, subject_confidence, jail_break_attempt (0.0–1.0), wish_i_knew, business_rules_triggers, refs — see v2/base/base-4/BIBLE.md.
      • 
            
    
            
    Layer B — server report: attribution + decision + report (metrics, spans, …) + stored_at. Model does not emit Layer B. See Structure → chapter 4.
    
          
    

          
    
            
    base-1 and base-4 in this inspector?
    
            
    One index.html lists every v2/**/chat_request*.json (rescan with scripts/scan_catalogs.py). Use the mode dropdown (folder · mode · base_id) and Diff / Matrix to compare base-1 vs base-4. Do not maintain a separate index-base-4.html for catalog mapping. Migration map: v2/base/base-4/BASE_1_TO_BASE_4_GUIDE.md.
    
          
    

          
    
            
    Why is guidance yellow / missing on min?
    
            
    Min drops bulky GREEN guidance to save tokens. Rules + injects still run. Put durable policy in Hub injects.
    
          
    

          
    
            
    What is the evidence loop in one sentence?
    
            
    Log every terminate’s query_decomposition, cluster success/failure intents, improve catalog/injects, re-stamp — not prompt folklore.
    
          
    

          
    
            
    Can I edit the JSON in this repo by hand?
    
            
    Baselines are generated in Zeus then published here. Prefer fragments → regenerate → publish.

    Troubleshooting
    
            
      
              
    • Empty answers / invented fields — fix entity map / MINI-SCHEMA, not only the system prompt.
      • 
              
    • Slow or expensive chats — too many search/hybrid calls; prefer pipeline; trim verbs.
      • 
              
    • Contract / hash errors — re-stamp and rebind the client.
      • 
              
    • Missing query_decomposition — terminate envelope incomplete; check RED messages + return/pipeline props.
      • 
              
    • project rows missing:true — projection / bag / entity map issue (ops), not only the prompt.
      • 
              
    • Page won’t load data — serve over HTTP from repo root (python3 -m http.server 8766), not file://.
      • 
              
    • Light mode hard to read — hard-refresh after updates; theme Auto follows the OS.
