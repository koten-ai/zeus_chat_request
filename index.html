Simple picture: how it fits together

          
You ask a question
        │
        ▼
  Zeus Client (or Hub chat)
        │  1) load chat_request_*.json  (this file = menu + house rules)
        │  2) inject BLUE pieces: scope brief, mini-schema, business rules, your message
        │  3) call the LLM with tools (verbs)
        │  4) LLM calls Zeus APIs (find / search / pipeline / …)
        │  5) LLM terminates with STANDARD output fields
        ▼
  Answer + query_decomposition (for analytics) + refs

          
This repo holds baseline templates (by mode). Your production file is refined in Hub Workbench and stamped on your Zeus so the hash matches what you deploy.


          
Color policy (cards = tree = JSON)

          
    
            
  • RED — Rules. Shipped in the catalog; changing them changes the contract hash. Edit only via Zeus generator / deliberate release.
    • 
            
  • GREEN — Editable guidance. Business-friendly advice (optimal paths, facet docs). Hash-excluded on full profiles. Often missing on min (yellow card).
    • 
            
  • BLUE — Injected at runtime by Zeus Client / Hub (not stored in the baseline JSON). Competes for tokens with the red system prompt.
    • 
            
  • PURPLE — Meta / stamp labels (id, hash, notes).
    • 
            
  • YELLOW — Present on full profiles, missing on this min file. Not an error—min is intentionally lean.

Glossary A–Z (plain language)

          
Same color borders as Cards / Size map / JSON blocks. Left border: red = rules, green = editable, blue = injected, purple = meta.

          

            
@as.ids
How pipelines pass IDs between steps (e.g. find → project). Wrong shape = empty results.

            
A/B / eval pack
Compare two catalog stamps (or injects) on the same questions before promoting to production.

            
Baseline vs stamped
Baseline = GitHub template. Stamped = verified on your Zeus with a server hash for production binding.

            
Boundary / scope
Hard wall: the model may only touch data in the bound bucket/scope. Stops cross-tenant leaks.

            
Bucket
Couchbase data container. Zeus scopes sit on buckets; chat never invents a bucket outside the bound session.

            
Business logic / prompt_override
Your company language & policies. Injected (BLUE) from Hub/Workbench—not hard-coded into public baselines.

            
chat_request*.json
The menu + house rules the AI sees: tools it may call + how to answer. One file per mode.

            
Cheap vs expensive verbs
find/get are cheap; search/analyze cost more. Prompt steers “cheapest first” so chats stay fast and affordable.

            
confidence
Required terminate field: only the strings high, med, or low (not a float). Used for analytics and UX badges.

            
Contract / stamp / hash
Server fingerprint of Rules. Clients send contract_id + contract_hash every turn to detect drift.

            
Contract drift
Client rules no longer match the stamped hash—someone changed the catalog without rebinding.

            
decomposition
Structured data plan (targets, predicates, output type) grounded in MINI-SCHEMA. Required on terminate.

            
DCP / projection
How Zeus keeps graph bags (nodes/edges) in sync with source documents. Entity map drives what gets projected.

            
Entity map
Operator map of fields → types/FKs. Feeds projection + what appears in MINI-SCHEMA.

            
entity_types / edge_types
Denormalized type lists on graph docs so filters avoid full primary scans. Ops/index concern, not model prose.

            
Envelope (V2)
The chat_request.v2 shape: Rules + optional guidance + wire/inject slots. Same envelope, different modes.

            
Evidence loop / hot-path
Product loop: capture real turns → cluster success/failure paths → improve catalog → A/B. Needs query_decomposition.

            
find vs search
find = exact/filter (cheap). search = FTS/vector/hybrid (expensive). Prefer find when filters exist.

            
FTS / hybrid / vector
Text search, embedding search, or blend. Powerful but costlier than keyed find—model should use when filters alone fail.

            
get / bag / graph
Fetch projected node/edge bags after you know IDs. Graph verbs explore relationships; don’t start there blindly.

            
Guidance
GREEN advisory block (optimal paths, facet docs). Often hash-excluded; often stripped on min.

            
Hash policy
Which JSON paths are Rules vs excluded when stamping. Lets guidance change without always breaking clients.

            
Hub / Workbench
Operator UI on Zeus admin to refine catalogs, inject business text, stamp contracts, run chat A/B.

            
instructions
Structured rules (response_expectations, verb_order). Full profiles; min often folds essentials into messages.

            
Intent facets
Slots like intent, entity, geo, audience—the shape of query_decomposition for clustering questions.

            
LLM / tool-calling
The model does not run N1QL itself; it chooses allowed verbs; Zeus Client executes them and returns facts.

            
masq
Cost tiers for verbs (cheap/mod/expensive). Helps the model pick cheaper tools first.

            
manifest.json
Index of modes + byte sizes in this repo. The UI loads it first, then the chosen v2/min/…json.

            
min vs full
min (this repo) = smaller client payload. full = engine snapshots with guidance/instructions bulk.

            
MINI-SCHEMA / scope brief
Live description of your entities/fields/counts. Injected so the model doesn’t invent columns.

            
Mode
Profile of behavior (analytics, fraud, auto…). Same envelope shape; different defaults and tool emphasis.

            
optimal_paths
Suggested multi-step tool recipes for common intents. Guidance (green), not hard-coded execution.

            
pipeline
One server-side multi-step call (find→order→project). Preferred over many chat rounds.

            
PROMPT_BUILDER / fragments
How Zeus engineers assemble system prompts from versioned pieces (not hand-pasted 5k-line monoliths).

            
query_decomposition
Required terminate object: business intent facets (intent+entity…). Powers hot-path analytics.

            
return / return_result
Terminal verb: model stops and emits the standard output schema (summary + decompositions + confidence).

            
Rules (hashed)
What production promised: messages, verbs, masq, etc. Change ⇒ new hash.

            
ScopeConfig
Per-scope operator config (auth, endpoints, injects, entity map). Where business language lives in production.

            
Standard output schema
Same required terminate fields across modes/deploys so every call is machine-parseable.

            
System prompt (messages)
Operating instructions the model reads from the catalog (RED). On min, must carry evidence-loop rules.

            
Token budget
Context window is limited. RED system + RED verbs + BLUE injects + history all compete—Size map shows the fight.

            
Tool result / multi-round
After each verb, Zeus returns facts into the conversation; the model may call more tools or terminate.

            
verbs / tools
Allowed Zeus API functions for the model. No verb ⇒ no safe access to that capability.

            
Wire payload
What actually goes to the LLM: catalog system+tools plus BLUE injects and conversation—not the whole pretty JSON file.

            
zeus_chat_request repo
Published baselines for clients without cloning the engine. This UI maps that structure.

            
Zeus Client
Middleman: loads catalog, injects blue context, calls LLM, executes verbs on Zeus, returns answers.

            
Zeus engine / Hub
Engine serves APIs + projection. Hub is the operator admin UI (status, scope config, chat workbench).

FAQ

          
What is the difference between AUTO, ANALYTICS, FRAUD, … in the dropdown?

          
Each file is a mode profile: same envelope idea (tools + rules), different emphasis.

          
    
            
  • analytics — default “real links, not noise”; balanced graph + semantic tools. Most demos start here.
    • 
            
  • auto — discovery / safe-during-setup; not a long-term production mode.
    • 
            
  • fraud — keep more weak signals; graph structure matters more; lower confidence floor.
    • 
            
  • code — code/doc style exploration.
    • 
            
  • research / open — more exploratory tool mix.
    • 
            
  • tenant / private / regulated — stronger tenancy / privacy / compliance posture in the product stack.
    • 
            
  • custom — shell for operator-tuned modes.
    • 
          

          
This dropdown only switches which baseline you inspect. Production: assign a mode per scope in Zeus.


          
Where do I put “talk about my business” for the AI?

          
    
            
  1. Hub Workbench / scope config — business injections, prompt overrides, entity map labels (preferred, BLUE at runtime).
    2. 
            
  2. guidance on a full catalog (optimal_paths, notes) — GREEN, often hash-excluded.
    3. 
            
  3. Not by forever hand-editing RED messages/verbs in this public baseline if you care about stamp stability—use Zeus generator + Workbench, then stamp.
    4. 
          


          
How do I optimize chat_request?

          
    
            
  1. Use Size map: shrink what dominates tokens (usually system prompt + tools).
    2. 
            
  2. Prefer min for clients; keep evidence-loop terminate fields (query_decomposition required).
    3. 
            
  3. Push domain knowledge into MINI-SCHEMA + blue injects, not a 50-page system essay.
    4. 
            
  4. Use pipeline / cheaper verbs; don’t expose tools you don’t need for that mode.
    5. 
            
  5. Stamp on Zeus; A/B with eval packs before swapping production hashes.
    6. 
          


          
What is “schema output standardization”?

          
No matter which mode or which deployment, when the model finishes a turn it must emit the same structured envelope (at least):

          
    
            
  • summary — human answer facts
    • 
            
  • query_decomposition — business intent facets (intent + entity + …)
    • 
            
  • decomposition — data targets/predicates from MINI-SCHEMA
    • 
            
  • confidence — string high|med|low only
    • 
          

          
That way every call, every environment, can be logged, compared, and fed into hot-path analytics the same way. See the green “Standard output” panel on the Cards tab.


          
Why is guidance yellow / missing on min?

          
Min profiles drop bulky green guidance to save tokens. Rules (red) + injects (blue) still run. Put durable business policy in Hub injects; use full profiles when you need green optimal_paths in-file.


          
Why do RED / GREEN / BLUE sizes matter?

          
Every byte in the wire payload costs latency and money. RED is the fixed menu; BLUE is live truth for your tenant; GREEN is optional coaching. If BLUE+RED already fill the window, history and long answers get truncated—use Size map to see the fight before you ship.


          
What is the evidence loop in one sentence?

          
Log every terminate’s query_decomposition (and outcomes), cluster which intents succeed/fail, then improve verbs/guidance/injects and re-stamp—not “prompt folklore.”


          
min file vs full file — which do clients load?

          
Clients should load the stamped min (or equivalent slim profile) from your Zeus, not necessarily this GitHub copy. Full snapshots live in the engine for authors; this repo publishes mins for transparency and client pinning.


          
Can I edit the JSON in this repo by hand?

          
Baselines are generated in Zeus (make ai-snapshot-min) then published here. Prefer editing Zeus prompt fragments / generator, regenerate, publish—don’t maintain a second hand-edited truth.


          
How do expand/collapse and the content panel work?

          
    
            
  • JSON ▾ toggles only that section’s body (keeps the page scannable).
    • 
            
  • Expand all / Collapse all toggles every section at once.
    • 
            
  • Clicking a section header opens the sticky panel with full text + bytes/~tokens.

Troubleshooting (common “why?”)

          
    
            
  • Empty answers / invented fields — MINI-SCHEMA or entity map incomplete; model is guessing columns. Fix ScopeConfig / entity map, not only the system prompt.
    • 
            
  • Slow or expensive chats — too many search/hybrid calls; trim verbs; push optimal_paths / masq; prefer pipeline.
    • 
            
  • Contract / hash errors — client still pins old stamp after catalog change. Re-stamp and rebind client.
    • 
            
  • Missing query_decomposition in logs — min system prompt lost evidence-loop rules, or model terminated without the schema. Check RED messages + return verb description.
    • 
            
  • Cross-scope leakage fears — boundary is server-enforced; still never put secrets in RED baselines that ship to every client.
    • 
            
  • This page won’t load data — must be served over HTTP from the repo root (e.g. python3 -m http.server 8766), not opened as a file:// URL.
